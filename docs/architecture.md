# Архитектура проекта

## 1. Общая схема

Проект сделан как модульный монолит. Приложение запускается одним процессом, но код разделён по назначению.

```text
Клиент
  ↓
API (FastAPI)
  ↓
PredictionService
  ├── preprocessing
  ├── ModelLoader
  └── PredictionRepository
```

## 2. Контуры из задания

### DataOps

На вход приходит телеметрия оборудования. Сейчас она передаётся прямо в REST-запросе. Схема данных проверяется перед расчётом.

### MLOps

Отдельный модуль `app/ml` отвечает за подготовку признаков и вызов модели. В учебной версии вместо настоящих весов используется простой расчёт риска.

### Application & Serving

FastAPI принимает запрос, проверяет API key, валидирует JSON и вызывает `PredictionService`.

### DevOps и наблюдаемость

Для запуска подготовлен Dockerfile. Метрики отдаёт Prometheus endpoint, а логи настраиваются как JSON.

## 3. Поток запроса

1. Клиент отправляет JSON на `/api/v1/predict`.
2. FastAPI проверяет ключ и схему данных.
3. `PredictionService` вызывает preprocessing.
4. `ModelLoader` рассчитывает результат.
5. Формируется `request_id` и определяется необходимость ручной проверки.
6. Результат сохраняется в репозитории.
7. Клиент получает JSON-ответ.

## 4. Train-Serving Skew

В учебном проекте преобразование признаков вынесено в отдельный файл. Если модель будет обучаться отдельно, этот же код или общий артефакт преобразований нужно использовать и при обучении, и при инференсе. Иначе модель может получать признаки в другом виде.

## 5. Ограничения

Сейчас нет очереди сообщений, внешнего реестра моделей и постоянной базы данных. Для лабораторной работы эти части не нужны, поэтому они оставлены как возможные направления развития.
